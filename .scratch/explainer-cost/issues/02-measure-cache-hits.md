# 实测缓存命中、真实输出用量与 DB 缓存命中率

Type: task

Blocked by: 

Status: resolved

## Question

票 01 用真实 BPE 量清了 prompt 尺寸与 provider 机制（见 [`provider-cache-matrix.md`](../provider-cache-matrix.md)），但成本结构里最重的一项——**实际输出 token 数**——仍是估算（~2,000）。本票用真实调用把这几个数字坐实：

1. **缓存真的命中吗**：在一个门槛满足的通路上（首选 **DeepSeek**，门槛 64 tokens、省 98%、全自动零代码；次选 OpenAI，门槛 1,024、1,219 刚过），同一 `(L, M)` 下连续讲解两段不同文本，读 `result.usage.inputTokenDetails.cacheRead`（openai-compatible 路径）确认第二次是否出现缓存读。
2. **真实输出分布**：thinking **off**（默认）下，实际输出 token 落在什么区间？`simple` + notes + grammar + `translationM` 各占多少？输出成本占总成本的实际比例（票 01 估的是 81%）？
3. **上限风险到底有多大**：thinking 各档位的实际输出 token 与最坏情况（40,960 上限）差多远？——这直接支撑票 04。
4. **DB 缓存命中率**：重复选段确实零网络请求（`ExplainerService.ts:91`）已由代码确认；本票补上**真实阅读场景下的命中率**（同一会话内不同选段的占比），因为它决定了 prompt 缓存与输出侧优化的**残余流量基数**。
5. **两条通路一致性**：Tauri 直连与 web `/api/ai/explain` 的缓存行为是否一致（provider 装配不同）。

方法与约束：

- **不需要改产品代码**。`result.usage` 目前完全未读，可用一段临时脚本直接对 provider 发同形态请求取数；若确实要在产品里落遥测，那属于票 05 的决策范围，不在本票。
- 需要真实 API key，因此本票可能是 **HITL**：若 key 需人工提供，请给出**精确到可复制粘贴的操作步骤**，让用户一次跑完并回报 usage 数字。
- 产物不入库（或落在本 effort 下的临时文件），只把数字写进 `## Answer`。

产出：一组可引用的实测数字（缓存命中与否、输出 token 分布与占比、DB 命中率），写入本票 `## Answer`。

## Answer

**方法**：脚本直接 `import` 真实的 `buildExplainerSystemPrompt` / `buildExplainerInputPrompt`（非副本），对 `https://api.deepseek.com/chat/completions`（`deepseek-chat`，temperature 0.2，max_tokens 4096，thinking off）发 4 次请求。选段为真实 Gutenberg 原文各 **500 词**（对应 `EXPLAINER_INPUT_LIMITS.maxUnits`）。4 次调用合计不到一分钱。

### 1. 缓存确实命中——你最初的直觉成立

| 请求 | 输入 | **cache hit** | cache miss | 输出 | 命中率 |
| --- | --- | --- | --- | --- | --- |
| R1 选段 A（冷启动） | 1,884 | **0** | 1,884 | 2,699 | 0% |
| R2 选段 B（**同** system） | 1,842 | **1,024** | 818 | 2,874 | **54.4%** |
| R3 选段 A（同 system，输入与 R1 完全相同） | 1,884 | **1,664** | 220 | 2,294 | **88.3%** |
| R4 选段 A，`nativeLang=ja`（不同前缀，对照组） | 1,874 | **0** | 1,874 | 3,309 | 0% |

- **R2 是现实场景**（同一本书、同一语言组合，用户划了另一段）：**1,024 tokens 命中**，占输入的 54.4%。**零代码改动即命中**——不需要"复用会话"，印证票 01 的判断。
- **R4 是对照组**：只把 `nativeLang` 从 `zh-CN` 换成 `ja`，命中立刻归零 → 缓存严格按**前缀逐字节**判定，换语言组合即失效（也说明"扩大跨语言复用"确有理论价值，但票 01 已算出其上限只有 1.6% 前缀）。
- R3 的 88.3% 是输入完全重复的情形——**但在真实 app 里这种情形由 DB 缓存兜成 $0，根本不会发请求**，所以它不是有效收益。

### 2. 真实输出 token 远高于票 01 的估算

实测输出 **2,294 / 2,699 / 2,874 / 3,309**，均值 ≈ **2,794**。票 01 估的是 ~2,000，**低估约 40%**。这意味着输出占账单的比例比票 01 算的还要高。

**附带风险**：R4 的 3,309 tokens 已达 thinking-off 上限 `maxOutputTokensOff = 4,096` 的 **81%**。复杂选段存在**触顶截断**风险——截断会打断 JSON，落到 salvage 兜底路径。这条已转交 [输出预算收敛与截断风险治理](../../explainer-output-budget/issues/01-output-budget.md) 评估。

### 3. 两次独立测量互相验证

实测 `prompt_tokens = 1,884`，与票 01 用真实 BPE 预测的 **1,219（system）+ 665（选段）= 1,884** **逐 token 吻合**。两个独立测量口径一致，数字可信。

### 4. 省费量级：确认缓存是小杠杆

- **输入成本降 51.1%**（R2 相对冷启动，`0.00052752 → 0.00025771` 美元/次）。
- **等输出口径的总成本降 ~16%**。（脚本摘要里的 11.8% 是 R1→R2 的原始差值，被 R2 多出的 175 个输出 token 混淆了，不是纯缓存效应。）
- **输出占账单 68.2%**（DeepSeek 价格比仅 1.5×）；在 4× 价格比的 provider（Gemini 2.5 Flash-Lite / OpenAI）上按同样 token 数会升到 **~85%**。

### 5. 与价格表无关的事实（可跨 provider 引用）

- 输出:输入 **token 比 = 1.43**；只要输出单价 ≥ 输入单价的 **0.70 倍**，输出就占账单过半。可达集合全部远超这条线（OpenAI 4×、Anthropic 5×、Gemini 4×、DeepSeek ~1.5×）。
- 完美缓存整个 1,219-token system prompt 的省费上限 ≈ **18.5%** 总账单（DeepSeek 价格比下；Gemini 4× 比下约 8.7%）。

### 6. 未能测量的部分（诚实标注）

- **DB 缓存命中率**：需要真实阅读场景的遥测（同会话内不同选段的占比），脚本无法提供。它是 03 折算残余流量时的必备输入，仍是空白。
- **两条通路一致性**：本脚本走裸 OpenAI 兼容 HTTP，等价于 app 的 `openrouter` 路径；web `/api/ai/explain` 用同样的 provider 构造但未实测。
- **价格绝对值**：沙箱 DNS 把 `api-docs.deepseek.com` 解析为非公网 IP，官方价目表取不到。搜索显示 DeepSeek 恰在 **2026-09-10 调整 Flash 系列定价**，故本票只把**与价格表无关的 token 事实**作为结论，美元数字标为"假设价、待核"。

### 结论

**缓存能命中、且零代码改动——但只值总账单的 12–19%，不是数量级的节省。** 输出侧（单次实测输出已达 4,096 上限的 81%）与已有的 DB 缓存才是大头。这条实测数据支持 03 把重心移出缓存。
