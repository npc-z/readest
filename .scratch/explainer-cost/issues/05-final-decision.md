## Answer

**决策（用户于 2026-09-10 作出）：prompt 缓存不做。**

### 直接回答最初的问题

> **"复用上一次的会话能否命中缓存、从而节省费用？"**

**能命中，但不需要"复用会话"，而且省的钱不值得为它做任何事。**

- **命中是真的**：票 02 用 DeepSeek 实测，同 system prompt、换选段时 **1,024/1,884 = 54.4% 输入命中**；对照组（换 `nativeLang`）命中归零，证明缓存严格按前缀判定。**零代码改动**——前缀稳定这一条在现有实现里早已成立。
- **"复用会话"是多余的**：多轮会话不是命中缓存的前提；真去做反而会让输入随轮次线性增长。
- **量级不够**：输入成本降 51.1%，等输出口径总成本降 **~16%**，上限约 **12–19%**。理由是输出占账单 68–85%，system prompt 只占 12.3%。

### 决策在两条分支上都成立（这是它稳健的原因）

1. **能自动命中的 provider**（DeepSeek / OpenAI / OpenRouter 透传）：本来就免费命中，**无事可做**。
2. **默认托管模型**（gemini-2.5-flash-lite）：受 Gemini 2,048-token 门槛限制，**根本不可能命中**（请求仅 1,884），且 Flash-Lite 未列入官方门槛表——**代码无解**，唯一"办法"是把 prompt 写长，那不是省钱。
3. **剩余可选改动**（为 Anthropic 加 `cacheControl`、为 OpenRouter 加 `prompt_cache_key` 稳定粘性路由）上限同样只有 12–19%，低于任何合理门槛；且 app 无原生 Anthropic SDK，实际触达面很窄。

### 本票的两张前置票如何处理

- **[降本门槛与优先级](03-cost-bar-and-priority.md)**：其"缓存是否值得做"部分被本决策直接吸收（结论：不做）；其"输出侧"部分迁往独立 effort。故该票不再单独解析。
- **输出侧降本**：**不随本图关闭**，已迁出为独立地图 `../explainer-output-budget/`，因为它承载的是**质量事故风险**（实测输出达 thinking-off 上限 4,096 的 81%，截断会掉进 salvage 兜底），而非成本问题。

### 交接输入

**缓存方向：无实现工作。** 不需要改动 `prompts.ts`、`gateway.ts`、`explain/route.ts` 或任何 provider 配置——自动缓存在用户把通道指向 DeepSeek/OpenAI 时自行生效。

若将来重估，触发条件有二：(a) prompt 因故大幅变长并越过各家门槛；(b) 发现通往 Anthropic 等需显式标记的 provider 的原生通路。两者都不在当前路线图上。
