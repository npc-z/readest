# 降本门槛与优先级：缓存 vs 输出侧

Type: grilling

Blocked by: 02

Status: resolved

## Question

票 01 已经把成本基线算清楚了（[`provider-cache-matrix.md`](../provider-cache-matrix.md) §5）：典型调用 ~$0.00099，其中**输出 81% / 输入 19%**，整个 system prompt 只占 **12.3%**。所以本票不再是"算基线"，而是**在已知基线的前提下定门槛与排优先级**：

1. **门槛数值**：省到什么程度才算"值得做"？给出可判定的数值（如"总成本降 ≥ X%"或"单次省 ≥ $Y"）。**BYOK 与托管两个视角分别定**——前者省的是用户配额体验，后者是 Readest 的真金白银，门槛不该相同。
2. **"不做"条件**：明确什么情况下直接判"不做"。已知 prompt 缓存的上限是 **~11%**（DeepSeek ~25%）且默认模型 **$0**——这个量级是否已经低于你的门槛？
3. **优先级排序**：在同一门槛下比较三条路的"省费 / 实现成本"比：
   - a. prompt 缓存（零代码自动命中 vs 为 Anthropic 加 `cacheControl` vs 为 OpenRouter 加 `prompt_cache_key` 稳定粘性路由）
   - b. 输出侧/参数侧（thinking 上限 40,960 的风险治理、`maxOutputTokens` 收敛、prompt 瘦身）——**票 01 判定它是 5–10 倍于缓存的杠杆**
   - c. 补上用量遥测（`result.usage` 未读，今天无任何可观测性）
4. **残余流量折算**：收益必须按 02 实测的**残余流量**（同会话内不同选段）折算，不得拿全部讲解次数当基数——重复选段已被 DB 缓存兜成 $0。

约束与提示：

- 门槛必须**在知道最终结论之前**定下，否则等于没有门槛。
- 若 prompt 缓存的量级已低于门槛，本票应直接给出"缓存不做"的建议，把重心移到输出侧——这正是终点允许的结论。
- 不要重算票 01 已有的基线数字；如需引用直接链接产出物。

产出：一组门槛数值 + 明确的"不做"条件 + 三条路的优先级排序，写入本票 `## Answer`。

## Answer

**本票未被独立解析——被 [最终决策：做 / 不做 / 做什么](05-final-decision.md) 直接吸收。**

用户在原图实测数据（票 02）到手后直接作出判断：缓存既然零代码改动就能命中、且上限只有总账单 12–19%，就不值得为它设定门槛或继续排序。因此本票问的"缓存 vs 输出侧的门槛与优先级"中：

- **缓存部分**：结论为**不做**，理由与被否决的备选见 05 的 `## Answer`。
- **输出侧部分**：迁往独立地图 `../explainer-output-budget/`（承载的是截断质量风险，不只是成本）。
