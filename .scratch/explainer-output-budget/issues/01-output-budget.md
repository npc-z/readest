# 输出预算收敛与截断风险治理

Type: grilling

Blocked by: 

Status: open

## Question

原图的实测把输出侧从"次要杠杆"变成了"既是大头成本、又是质量事故风险"。本票把方案与边界定下来：

1. **截断风险怎么治**：实测输出已达 2,294–3,309 tokens，而 thinking-off 上限是 **4,096**——**最坏的一次占满了 81%**。选段更长或文本更复杂时就会触顶，JSON 被打断、掉进 salvage 兜底、用户拿到残缺讲解。可选方向：
   - 把上限抬到安全余量（如 6,144），代价是尾部成本敞口变大；
   - 收敛上限到与实际分布匹配的数值（如 3,072）——但这会**主动制造**截断，与目的相反；
   - 维持 4,096，但**检测截断并显式暴露**（`finish_reason: 'length'` 或 JSON 不完整时提示"讲解不完整，请重试/缩短选段"）；
   - 组合：略抬上限 + 截断检测。
2. **thinking 档位的成本敞口**：thinking ≠ off 会把上限抬到 **40,960**（10×）。用户打开它就承担了"一次满预算 = 典型调用 16.6 倍"的尾部风险。是否需要：
   - 收敛 thinking 档位下的上限（如 8,192 / 12,288）？
   - 保留上限但加用量告警/熔断？
   - 维持现状，只保证默认 off？
3. **prompt 瘦身**：system prompt 里 **TASK 段 710 / 1,219 tokens（58%）**、OUTPUT FORMAT 235。在不降质的前提下这两段能压缩多少？注意输入只占账单 19%，所以这是**次要**杠杆——除非它同时能降低截断风险。
4. **质量边界**：以上任何调参如何验证"四级级联不降质"？定出可执行验收：
   - 用哪些选段（文学/技术/口语？多长？是否包含已知会产出 3,000+ tokens 的长段）
   - 什么标准（四级齐全、`meaningL` 是否比原词更简单、grammar ≤2、JSON 结构合规、有无截断）
   - 由谁判定
   - 建议复用原图实测用的那两段 500 词 Gutenberg 文本作为基线样本，便于前后对比。
5. **优先级与取舍**：以上方向中哪些是"防事故"（必须做）、哪些是"省钱"（可选）？给出建议排序。

约束与提示：

- 质量是硬门槛（见 `map.md` 已定前提）：任何调参若使四级级联降质，即为不可接受，无论省多少。
- 不要重算基线，直接链接 `../explainer-cost/provider-cache-matrix.md` 与 `../explainer-cost/issues/02-measure-cache-hits.md`。
- 本票只做方案与边界决策，**不实现**。
